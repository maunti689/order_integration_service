# Архитектура сервиса

## Приём заказа

1. Заголовок `X-API-Key` определяет активного B2B-клиента.
2. API приводит запрос к каноническому виду и рассчитывает его fingerprint.
3. Сервисный слой проверяет товары, активность каталога и валюту.
4. Заказ, снимки цен и outbox-событие `order.submission_requested` фиксируются одной
   транзакцией.
5. API возвращает статус `validated`, не ожидая доступности внешнего поставщика.

## Асинхронная передача

1. Celery Beat каждые пять секунд запускает обработчик outbox.
2. Обработчик блокирует небольшую пачку неопубликованных событий и отправляет задачи в
   RabbitMQ.
3. Worker сохраняет `ProviderRequest` до выполнения HTTP-запроса.
4. Временные ошибки повторяются с увеличивающейся задержкой; постоянный `4xx` переводит заказ
   в `rejected`.
5. Успешный ответ сохраняет идентификатор поставщика и переводит заказ в `submitted`.

## Обработка webhook

1. HMAC-SHA256 проверяется по исходному телу HTTP-запроса.
2. `provider_event_id` сохраняется под unique constraint.
3. Строка заказа блокируется на время монотонного перехода статуса.
4. Повторное или устаревшее событие получает ответ `2xx`, но не вызывает повторный эффект.

## Границы согласованности

- PostgreSQL хранит статусы заказов, дедупликацию и незавершённые outbox-события.
- RabbitMQ доставляет задачи как минимум один раз, поэтому обработчики остаются идемпотентными.
- Результаты Celery-задач не сохраняются: фактический результат обработки записывается в PostgreSQL.
- Поставщик должен соблюдать ключ идемпотентности, равный внутреннему ID заказа.
